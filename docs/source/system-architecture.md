# ISS Constructor V2\n\nSystem Architecture Specification — engineering baseline\n\nStatus: Baseline after architecture decisions A-001…A-036. This document defines implementation boundaries and invariants. Product behavior remains governed by the Product Specification and source requirement registries where not superseded by later architecture decisions.\n\n### 1. Architectural goals and invariants\n\n- Installation-first, fixed-resolution museum runtime. Responsive web breakpoints are not a core architecture requirement.\n\n- Constructor and Player are independently deployable Electron applications. Preview and Player execute the same Runtime Engine source.\n\n- Project authoring state, editor UI state and runtime state are separate models.\n\n- Runtime behavior is expressed through Triggers, Behavior Flows, Actions, Variables, Timelines, Widgets and Media systems rather than per-project custom code.\n\n- Build is an immutable, self-contained runtime snapshot. Player never depends on development-machine source paths and never edits the Build.\n\n- Failures are isolated as locally as practical: asset → widget/element → Screen renderer → whole Player.\n\n- Late architecture decisions supersede older Product Specification wording when they conflict; superseded requirements remain traceable rather than deleted.\n\n### 2. Repository and package boundaries\n\nISS/
  apps/
    constructor/
    player/
  packages/
    project-model/
    runtime-engine/
    actions/
    media/
    widgets/
    network/
    build/
    validation/
    shared/\n\nThe exact package split may evolve, but dependency direction must preserve the following rule: domain/runtime packages must not depend on React or Constructor UI. Constructor and Player consume shared packages; they do not duplicate runtime behavior.\n\n### 3. Electron process model\n\n### 3.1 Constructor\n\nConstructor Main Process
  ├─ filesystem / dialogs / OS integration
  ├─ heavy-operation coordinator
  └─ Constructor BrowserWindow Renderer
       ├─ React UI
       ├─ ProjectDocument bridge
       └─ Preview Runtime sessions\n\nNode integration is disabled in renderers. Context isolation is enabled. Privileged operations are exposed through a typed preload/contextBridge API. Heavy filesystem/build operations must not block Electron Main.\n\n### 3.2 Player\n\nPlayer Main Process
  ├─ local Player configuration
  ├─ Build loading/validation
  ├─ display discovery + window lifecycle
  ├─ TCP/UDP + multi-PC coordinator
  ├─ watchdog integration / renderer supervision
  └─ BrowserWindow Renderer per assigned Screen
       └─ one RuntimeSession for that logical Screen\n\nSame-PC multi-display uses separate BrowserWindows/renderers per logical Screen while the Player Main process coordinates shared runtime data and cross-Screen actions. Physical Display identity is deployment-local; project Actions target logical Screens, never monitor coordinates.\n\n### 4. Constructor state architecture\n\n### 4.1 Canonical ProjectDocument\n\nProjectDocument is the sole canonical editable project state. React components and Zustand stores must not mutate project entities directly. All project changes go through a controlled Project Operations API.\n\nUI intent → Project Operation → ProjectDocument mutation → History entry → reactive UI bridge\n\n- Project State: serialized authoring data.\n\n- Editor UI State: selection, open panels, viewport zoom/pan, transient dialogs; not project semantics.\n\n- Runtime State: Preview/Player execution state; never serialized back into ProjectDocument by ordinary runtime execution.\n\n### 4.2 Undo/redo\n\nHistory records reversible Project Operations. Runtime actions and editor-only UI changes do not enter project history. Large operations may use compound history entries.\n\n### 5. Project data model\n\n### 5.1 Identity\n\nIndependent/referenceable entities use stable IDs (UUID/ULID-like). Display names are mutable and never serve as identity. Owned value properties remain nested objects. Copy/Duplicate/Import remap copied IDs and internal references while preserving intentional external references.\n\n### 5.2 Main entities\n\n### 5.3 Versioning and migrations\n\n.iss contains formatVersion separate from appVersion. Supported older formats migrate sequentially in memory to the current model. The original file is not immediately overwritten; first Save after migration creates a backup. Older Constructor versions safely refuse unsupported newer formats.\n\n### 6. Working Project, assets and portable collection\n\nThe Working Project is a .iss authoring file. Assets may physically live anywhere on the development machine. The project stores stable asset IDs plus source paths and virtual Asset Library organization.\n\n- Ctrl+S does not copy all source media.\n\n- Virtual folders may be renamed/reorganized without moving physical source files.\n\n- Missing source files retain asset IDs and references and can be relinked.\n\n- Collect Project creates a portable editable project by copying ALL registered assets and rewriting source references to relative collected paths. It never moves originals.\n\nGlobal Components and Project Fonts must ultimately conform to the same asset/build model; no hidden dependency on machine-specific paths is permitted in a deployable Build.\n\n### 7. Build architecture\n\n### 7.1 Build pipeline\n\nProject snapshot
 → Full Validation
 → Runtime dependency resolution
 → source verification
 → Runtime Compiler
 → asset/font materialization
 → manifest generation
 → Build validation
 → atomic publish\n\nBuild uses a snapshot so editing may continue where safe without changing the in-progress Build. Only one conflicting heavy project operation runs at a time.\n\n### 7.2 Output\n\nBuild/
  project.json
  manifest.json
  assets/
  fonts/
  ...runtime dependencies\n\n- project.json contains Player-facing runtime data only; authoring-only state is removed.\n\n- Only runtime-used dependencies are copied into Build. Collect Project, by contrast, copies all registered assets.\n\n- manifest records Build ID, Project ID, runtime-format compatibility and asset metadata including stable ID/path/type/size/hash where available.\n\n- A missing used source asset is a Build Error. Unused missing assets do not block Build.\n\n- Failed Build never destroys the previous successful Build.\n\n### 8. Unified validation\n\nOne Validation Engine serves Open, Save-related checks, manual validation, Collect and Build. It returns structured Problems rather than modifying the project.\n\nValidation layers: schema → referential/semantic → resource/build. Problems carry entity/property context so Constructor can navigate to the affected object.\n\n### 9. Runtime state model\n\n### 9.1 Runtime definition vs runtime state\n\nPlayer-facing project.json is immutable Runtime Definition. Runtime execution creates mutable state in memory only.\n\nRuntime Definition (immutable)
        ↓
Player Runtime Coordinator
        ├─ RuntimeSession(Screen A)
        ├─ RuntimeSession(Screen B)
        └─ SharedRuntimeState\n\n### 9.2 Variable scopes\n\n- Page Runtime State — transient/local; destroyed on Page Leave.\n\n- Screen Session Variables — persist across Pages of one Screen; reset on Reset Screen / runtime restart.\n\n- Shared Runtime Variables — explicit shared state across Screens inside the same Player process.\n\nCross-computer variables are not implicitly shared. Persistent runtime variables on disk are deferred.\n\n### 10. Page lifecycle and navigation\n\nEnter → Active → Leave\n\nPage Leave cancels Page-owned delayed flows/timelines, stops Page-owned media/animations and discards temporary Page-local state. Re-enter creates a fresh Page runtime. Screen-level state survives.\n\n- Page Enter and Page Leave are standard triggers.\n\n- Navigation during transitions must remain deterministic and safe under rapid repeated input.\n\n- Navigate Page, Next, Previous, Go Back and Go Home are standard Actions.\n\n- Popups close as part of navigation according to lifecycle policy; Screen Media Player is handled separately.\n\n### 11. Trigger, Behavior Flow and Action architecture\n\nInput/Event → Trigger → Behavior Flow → Action handlers → Runtime State\n\nAll input sources converge on the same behavior engine: touch/pointer, keyboard, mouse, TCP, UDP, timeline events, media events, idle events and Widget events.\n\n### 11.1 Behavior Flow\n\nA Behavior Flow is an ordered sequence of Actions and Control Steps. Initial Control Steps are Delay and Condition/If. Delay is non-blocking and pauses only its own Flow.\n\n### 11.2 Action registry\n\nActions are registered by conceptual action type with optional target and typed parameters. The Trigger engine does not know implementation details. Initial families include Navigation, Popup, Media, Variables, Animation, Interaction, Element/State, Network, Timeline and Runtime/System actions.\n\n### 11.3 Ordering and cancellation\n\n- Events are accepted in arrival/event-loop order; there is no global busy flag waiting for visual effects to finish.\n\n- Stateful targets use ordinary latest-state semantics: later Set/Show/Hide/Play requests supersede prior state where appropriate.\n\n- Add/subtract and network sends remain cumulative operations.\n\n- Reset Screen cancels pending Page/Screen delays, timelines and future actions belonging to the old session.\n\n### 12. Media architecture\n\n### 12.1 Page media\n\nPages may contain multiple ordinary Image/Video/Audio media elements. Page background media is a normal supported runtime capability and may be Image, Video or Playlist.\n\nCritical V1 compatibility refinement: Page Background Video/Media supports autoplay, loop, mute/unmute and volume, including audible playback. Therefore V1 Screenless Mode is not a separate V2 runtime mode.\n\nNormal Screen
  Page "Idle"
    └─ looping Background Video + audio
         ↓ external Trigger
  Screen Media Player: Play Content
         ↓ finish/exit
  underlying Page "Idle" remains\n\nV1-F130 Screenless Mode is classified Revised/Covered: its user scenario is expressed by a normal Screen/Page plus audible background media and the Screen Media Player. No separate screenless/headless state machine is implemented for this purpose.\n\n### 12.2 Screen Media Player\n\nExactly one physical/system fullscreen Screen Media Player exists per logical Screen. It is Screen-owned, not Page-owned. Pages launch reusable Content through Actions. Starting new Content replaces/transitions the current system content rather than spawning another system player.\n\n- Page runtime continues underneath fullscreen content.\n\n- Page navigation while fullscreen content is active closes/stops it using Media Exit transition, then performs Page transition.\n\n- Stop/Exit reveals the current underlying Page unless an explicit Behavior navigates elsewhere.\n\n- Reset Screen closes/unloads system content.\n\n### 12.3 Playlist\n\nPlaylist is a first-class logical entity containing ordered asset IDs from arbitrary virtual/physical locations. Folder import is only a convenience for creating a Playlist. Playlist ordering is stored independently of the source filesystem.\n\n- Images use default/override duration; video uses natural duration with optional playback range/volume settings.\n\n- Loop cycles; non-loop completion exits content.\n\n- Current + next item may be prepared locally to make transitions reliable.\n\n### 12.4 Media Timeline\n\nMedia Timeline is driven by actual media playback time. Pause and seek affect its clock. Timeline points may run Behavior Flows. Loop-range crossings may fire events each pass.\n\n### 13. Page Timeline\n\nPage Timeline is relative to Page Enter and has no required finite duration. Auto-play starts at 00:00 on each Page Enter. Page Leave stops it. Events may be Every Page Enter or Once per Screen Session. Once flags reset with Screen reset/restart.\n\nPage Timeline continues while Screen Media Player or Screensaver visually covers the Page unless an explicit behavior stops it.\n\n### 14. Popup architecture\n\nPopup is a Page-owned runtime entity represented by a separate authoring frame. It contains ordinary Elements/Widgets and supports configurable backdrop, modality, open/close animation and input-close policy. Reuse across Pages is via Components, not global popup identity.\n\n- Open Popup, Close Popup and Close All are standard Actions.\n\n- On Open / On Close are standard triggers.\n\n- Navigate Page closes the active popup stack before transition.\n\n- Play Content closes popups before opening fullscreen system content.\n\n### 15. Screensaver and idle\n\nScreensaver is a Screen-level idle visual/input overlay, not a Page and not a substitute for normal Page state. It is intentionally simpler than a Page: background media plus limited overlay text/graphics/simple animation.\n\n- Each Page may define its own inactivity timeout or disable idle timeout.\n\n- Relevant processed user activity resets idle. Recognized network activity may count only according to configured behavior; raw network noise does not.\n\n- Idle activation closes transient popup/media as configured and shows Screensaver without Page Leave/Enter.\n\n- Hiding Screensaver reveals the current Page without re-entering it.\n\n- External triggers do not automatically hide Screensaver unless behavior explicitly requests it.\n\n### 16. Error and fallback architecture\n\nRuntime failure presentation is layered. Raw technical exceptions are never the visitor-facing UI.\n\nError Visual is a Screen-level system entity with simple reliable visuals and optional dynamic Error Code / Screen Name / human-readable message. Detailed asset IDs, paths, exceptions and recovery actions belong in logs/Dev Panel.\n\n### 17. Components\n\nComponents use versioned controlled propagation rather than live Figma-style mutation of every instance.\n\nComponent Definition revision N
      ↓ edit/save
Component Definition revision N+1
      ↓
Review & Apply Updates
      ↓
selected existing Instances update\n\n- Existing Instances do not silently mutate when the Component Definition changes.\n\n- Instance overrides have priority by default.\n\n- Structural conflicts require review.\n\n- Detach converts an Instance into ordinary independent elements.\n\n- Nested Components are allowed unless implementation testing reveals a concrete blocker.\n\n### 18. Widget architecture\n\nA Widget is a ready functional module with internal state and a widget-specific customization contract. It is not required to expose every internal part as ordinary Elements.\n\n- Gallery exposes content/order, viewport, controls, pagination, transitions and Gallery-specific Actions/Triggers.\n\n- Image Viewer exposes image, viewport, zoom/pan/reset behavior.\n\n- Quiz exposes questions/answers and visual states such as Normal/Selected/Correct/Incorrect/results.\n\n- Mini-games may internally use Canvas/WebGL but integrate through the common Widget contract.\n\nInitial V2 has an internal extensibility contract, not a public third-party SDK/marketplace.\n\n### 19. Component and visual styling systems\n\nProject visual styling uses project defaults, stable color variables and Project Fonts. Color references propagate when the referenced variable changes. Full runtime multi-theme switching is deferred.\n\nTTF/OTF Project Fonts are assets copied into Build and loaded by Player; Windows font installation is not required. System-installed fonts may remain available for V1 compatibility but are less portable.\n\nStructured SVG import targets ordinary SVG/Figma-exported SVG without special naming conventions; supported groups/primitives/text/transforms/styles are converted to editable structure, while unsupported constructs should preserve visual fidelity where practical.\n\n### 20. Media loading and performance\n\nInitial V2 deliberately avoids a global predictive HOT/WARM/COLD cache, LRU memory budget manager or dependency-graph preloader. The architecture uses Simple On-Demand + Targeted Preparation.\n\n- Startup prepares runtime/system essentials, Project Fonts, initial/current Pages as required, Screensaver and Error Visual resources.\n\n- Ordinary Page resources load on activation/preparation using normal Chromium/native media behavior.\n\n- Screen Media Player explicitly prepares content before playback and waits for required readiness.\n\n- Playlist may prepare current + next item. Widgets may perform small local neighbor preparation where appropriate.\n\n- Multi-PC synchronized playback always uses explicit PREPARE → READY → scheduled execution.\n\n- The media/asset API must leave room for a smarter Preload Manager later without changing authoring semantics or project identity.\n\nV1 broad preload behavior is therefore Revised rather than silently removed: V2 preserves readiness/progress/error handling where operationally necessary but does not require eager loading of every used asset.\n\n### 21. Single-PC multi-display\n\nOne Player process may drive multiple logical Screens on one Windows PC. Each assigned Screen receives its own BrowserWindow/runtime renderer. Player Main owns physical display discovery and local Screen→Display mapping.\n\n- At most one logical Screen per physical Display and one physical Display per Screen in the standard mapping model.\n\n- Mapping is stored in Player-local configuration, not the portable project.\n\n- Missing mapped monitor never causes silent remapping and does not stop other Screens.\n\n- Cross-Screen Actions use the Player Runtime Coordinator and logical Screen IDs.\n\n- Shared Runtime Variables are available across Screens inside the same Player.\n\n### 22. External TCP/UDP control\n\nTCP/UDP transport
   ↓
Network Service
   ↓
Incoming Trigger mapping
   ↓
Behavior Flow
   ↓
Action Engine / Runtime Coordinator\n\n- Raw payload strings are valid; JSON is not mandatory.\n\n- Multiple listening ports and named outgoing endpoints are supported.\n\n- Source IP and optional source-port filtering are supported.\n\n- Initial matching modes: Exact, Starts With, Contains. Regex is deferred.\n\n- Unknown messages are safely ignored and logged.\n\n- TCP framing is configurable; newline is the default. UDP is message-oriented and requires no framing.\n\n- Outgoing Send TCP / Send UDP are ordinary Actions.\n\n- Generic TCP/UDP is the initial iRidi integration path; dedicated adapter only if a real installation requires it.\n\n### 23. Multi-PC synchronized installation\n\n### 23.1 Topology\n\nMulti-PC is an installation topology, not a per-Action checkbox. Separate Player installations may run completely different Builds while participating in one synchronized installation.\n\nMaster / Server Player
   ├─ local Runtime
   ├─ expected Client registry
   ├─ clock-offset estimation
   └─ distributed execution coordinator
          ↕ persistent LAN connections
Client Player(s)
   └─ independent local Runtime + Build\n\n- Node identity should use stable nodeId; IP remains transport address/security restriction rather than sole identity.\n\n- Initial startup may wait for all Required Clients. Optional clients may be supported as a configuration distinction.\n\n- After installation is already running, loss of one Client does not freeze unrelated nodes. Missing-target actions fail safely and are diagnosed.\n\n- Reconnected Clients resynchronize clock and participate in future operations; missed history is not automatically replayed.\n\n### 23.2 Distributed execution\n\nDistributed Action
 → PREPARE (when preparation is needed)
 → READY barrier
 → choose future shared timestamp
 → EXECUTE AT timestamp
 → local Action Engine\n\nThis generalizes the proven V1 playback-sync pattern beyond media where synchronized timing matters, e.g. Navigate Page, Start Timeline or Start Animation. Purely local actions remain immediate; the system must not add synchronization latency to every click.\n\nSequence advancement may run another synchronization cycle. Continuous drift correction is not required initially; clock measurement/resynchronization and exact margins belong in the later Network/Sync engineering specification.\n\n### 24. Preview and developer runtime\n\nConstructor Preview is a full Developer Runtime using the same Runtime Engine as Player. Preview starts from a project snapshot; there is no requirement for live mutation of an already-running Preview session.\n\n- Physical Displays mode and All Screens Simulator mode are supported.\n\n- Simulator scales visual output while preserving actual designed resolution semantics.\n\n- Preview uses real TCP/UDP networking.\n\n- Developer overlay is a system layer and must not change project layout/viewport geometry.\n\n- Diagnostics include current Screen/Page, runtime variables, timelines, media/playlist state, idle/screensaver state, Action/Event trace, network monitor, manual network send and multi-PC sync status where applicable.\n\n### 25. Player setup, kiosk and local configuration\n\n### 25.1 Local configuration\n\nPlayer-local configuration is stored outside the installed application directory and survives normal application reinstall/update where compatible.\n\n- Selected Build path / project identity.\n\n- Screen→Display mapping.\n\n- Startup and developer settings.\n\n- Single-PC / Multi-PC mode, Master/Client role, node/network settings.\n\nThe exact storage format/path is an implementation decision, but it must be writable without modifying application binaries and must support atomic persistence.\n\n### 25.2 First run and maintenance\n\n- No project: show technician setup window → Select Build → validate → detect displays → configure mapping.\n\n- Normal subsequent launch: autostart → neutral/black fullscreen → load/prepare → runtime, with no visitor-facing technical UI.\n\n- Ctrl+Shift+D opens global Developer Mode using the physical key/code independent of keyboard layout.\n\n- Developer tools include Load another Build, Clear Project, Display Mapping, network/diagnostics and runtime status.\n\n- Display Mapping changes are staged and applied on Save; windows are created/closed/reassigned dynamically where safe without mandatory full Player restart.\n\n### 26. Fault isolation and recovery\n\n### 26.1 Screen-level isolation\n\nA crashed or persistently unresponsive Screen renderer is recreated independently. Other Screen renderers continue running. The recovered Screen starts a clean RuntimeSession at its known initial state; exact pre-crash Page/media/variable restoration is not required.\n\n### 26.2 Renderer responsiveness\n\nPlayer Main may use a conservative heartbeat between Main and Screen renderer. Multiple missed responses can mark the Screen unresponsive, log the event and recreate that Screen. Heavy synchronous work should be kept out of renderers to minimize false positives.\n\n### 26.3 Whole-Player recovery\n\nUnexpected whole-Player termination is recovered by an external Windows watchdog. The restarted Player reloads local configuration and Build, prepares resources and creates a clean Runtime Session. Watchdog design must include crash-loop protection.\n\n### 27. Runtime robustness under repeated input\n\nThe Runtime must remain safe under rapid touch, repeated network commands and conflicting user input. Stability is achieved by deterministic handlers/state semantics rather than a global interaction block.\n\n- Repeated Play does not spawn uncontrolled duplicate system players.\n\n- Opening the same popup cannot create uncontrolled duplicate instances unless explicitly designed.\n\n- Navigation requests during transitions resolve deterministically.\n\n- Legitimate cumulative actions such as Add Variable and Send Network Message still execute for each accepted trigger.\n\n- Interaction Lock is an explicit Action with scope; it is not a hidden stability mechanism.\n\n### 28. Application distribution and updates\n\nInitial V2 has no online updater, update server, remote deployment system or automatic rollback. Constructor/Player installers are delivered manually by the developer and installed/reinstalled manually by the responsible technician.\n\nThis is intentionally a deployment policy, not a permanent limitation: future update infrastructure may be added without changing project/runtime semantics.\n\n- Local Player configuration must survive compatible reinstall/update.\n\n- Player validates Build/runtime-format compatibility and refuses unsupported newer runtime data with a clear technician-facing error rather than attempting unsafe execution.\n\n### 29. Manual operations and concurrency\n\nConstructor does not implement a general-purpose parallel job scheduler in initial V2. One conflicting heavy project operation (Build, Collect, major import/migration) runs at a time.\n\n- Operations expose progress/status; Cancel is provided where safe.\n\n- Editing may continue when it cannot invalidate the operation snapshot.\n\n- Build and Collect operate on explicit snapshots, not a moving live ProjectDocument.\n\n### 30. Security and privilege boundaries\n\n- Electron renderers run with nodeIntegration=false and contextIsolation=true by default.\n\n- Filesystem, OS, display and raw network privileges live in Main/background services and are exposed through typed narrow IPC APIs.\n\n- Runtime project data cannot invoke arbitrary Node.js or OS code merely by containing project configuration.\n\n- Production Player suppresses visitor-accessible context menus, developer shortcuts and OS escape paths as far as the kiosk deployment allows.\n\nThis is an application architecture boundary, not a full hostile-content sandbox. Build inputs remain trusted project content produced by Constructor.\n\n### 31. Architecture compatibility dispositions\n\n### 32. Architecture acceptance criteria\n\nAC-ARCH-01  Constructor and Player compile/deploy independently while consuming the same framework-independent Runtime Engine source.\n\nAC-ARCH-02  Player can run a copied Build with no access to Constructor or development-machine asset paths.\n\nAC-ARCH-03  A multi-display Player isolates logical Screen renderers while coordinating shared local runtime state.\n\nAC-ARCH-04  Preview and Player produce equivalent runtime behavior for the same compiled Runtime Definition.\n\nAC-ARCH-05  All supported input sources can reach behavior through the unified Trigger/Behavior Flow/Action path.\n\nAC-ARCH-06  Fullscreen Screen Media Player works without owning Page state and cleanly reveals the underlying current Page on exit.\n\nAC-ARCH-07  A Page can use audible looping background video/media, covering the historical Screenless use case without a separate mode.\n\nAC-ARCH-08  Multi-PC synchronized operations use explicit distributed preparation/readiness/scheduled execution where timing matters.\n\nAC-ARCH-09  A single asset/widget/Screen failure does not unnecessarily terminate unrelated Screens or the whole installation.\n\nAC-ARCH-10  Build, validation, logs and Developer Mode make failures diagnosable by technicians without exposing raw technical UI to visitors.\n\nAC-ARCH-11  No confirmed V1 capability is considered removed merely because its V1 implementation mechanism was replaced; every V1-F item receives an explicit compatibility disposition/test.\n\n### 33.
