ISS CONSTRUCTOR V2\n\nProduct Specification\n\nCanonical product model and functional requirements
Version 2.0 • Draft baseline • 05 October 2026\n\nScope: Constructor • Working Project • Build • Player/Runtime • Content Admin • External Control\n\n### 1. Document purpose\n\nThis document defines the canonical product behavior of ISS Constructor V2: the entities users work with, the runtime model, functional capabilities, product boundaries, and compatibility obligations. It consolidates the original technical brief, the V1 Constructor/Player reverse-engineering baseline, reference ISS cases, and the V2 product decisions made during architecture discovery.\n\nThis is intentionally not a low-level implementation specification. Technology stack, process boundaries, storage implementation, IPC, rendering framework, schema internals, and deployment tooling may be designed later provided they preserve the behavior defined here.\n\n### 1.1 Normative principles\n\n- No confirmed V1 capability may disappear from V2 unless explicitly marked Removed. Current target: V1 regression = 0.\n\n- Preview and Player must execute the same Runtime Engine behavior.\n\n- Working Project and Player Build are distinct artifacts with a shared conceptual project model.\n\n- The product is installation-first and fixed-resolution; responsive web breakpoints are not a core requirement.\n\n- Project structure and logic are separated from visual styling wherever practical.\n\n- All runtime behavior should be expressible through reusable entities, events, conditions, actions, timelines, widgets, and media systems rather than per-project custom code.\n\n- If a reference ISS pattern cannot be built without custom application code, the platform is considered functionally incomplete for that pattern.\n\n### 2. Canonical terminology and hierarchy\n\n### 3. Product architecture\n\nThe V2 product consists of the following primary product surfaces:\n\n- Constructor — full authoring environment.\n\n- Content Admin Mode — restricted content-editing mode inside the same Constructor application.\n\n- Runtime Engine — common execution engine used by Preview and Player.\n\n- Player — standalone installation runtime consuming a Build.\n\n- Network Control — generic TCP and UDP triggers/actions plus synchronized multi-computer runtime facilities.\n\n### 3.1 Artifact lifecycle\n\nSource Assets → Working Project + Virtual Asset Library → Validate → Build → Player installation.\n\nPS-ARCH-001  Saving a Working Project must not implicitly perform a deployment Build.\n\nPS-ARCH-002  Building must create a self-contained Player project with no dependency on original development-machine asset paths.\n\nPS-ARCH-003  Player must execute only Player-facing build data, not Constructor-specific source paths.\n\nPS-ARCH-004  A Build must be transferable to installation hardware by copying the build directory.\n\n### 4. Constructor workspace\n\n### 4.1 Project management\n\nPS-PROJ-001  Create a blank project or create a project from a local Project Template.\n\nPS-PROJ-002  Open, save and save-as Working Projects.\n\nPS-PROJ-003  Manual save and Ctrl+S save the canonical Working Project.\n\nPS-PROJ-004  Recovery autosave is separate from the canonical saved project and must not silently overwrite it.\n\nPS-PROJ-005  After abnormal termination, Constructor may offer Restore Recovery versus Last Saved.\n\nPS-PROJ-006  Undo/Redo history is session-only and independent of save state.\n\nPS-PROJ-007  Project format contains an explicit projectFormatVersion and supports forward migration of older supported formats with backup before migration.\n\nPS-PROJ-008  Older Constructor versions are not required to open newer project formats.\n\n### 4.2 Screen Designer\n\nPS-DES-001  Each Screen owns an infinite Designer Canvas.\n\nPS-DES-002  Pages, Popups, Overlay Media Players and Screensavers may be spatially arranged as authoring frames on the Screen Designer Canvas.\n\nPS-DES-003  Page runtime size always equals Screen designed resolution.\n\nPS-DES-004  Canvas supports pan, zoom, fit-to-view, edit lock, grid and snap.\n\nPS-DES-005  Objects support select, multi-select, marquee, move, 8-direction resize, rotation, opacity, aspect lock, align, distribute and layer-order operations.\n\nPS-DES-006  Layers/Object Tree mirrors parent-child hierarchy, selection, Z-order, visibility, lock and reparenting.\n\nPS-DES-007  Containers may contain nested children, move/transform with children, clip content and optionally use Auto Layout.\n\nPS-DES-008  Auto Layout supports horizontal/vertical direction, gap, padding and alignment.\n\nPS-DES-009  Simple parent-relative constraints are supported; responsive breakpoint systems are outside initial V2 scope.\n\n### 4.3 Screen resolution changes\n\nPS-DES-010  Changing Screen resolution applies to all Pages in that Screen.\n\nPS-DES-011  Resolution change presents explicit transform choices rather than silently scaling the design.\n\nPS-DES-012  Supported strategies include preserving absolute position/size and proportional repositioning/scaling.\n\nPS-DES-013  Aspect-ratio changes generate a warning.\n\nPS-DES-014  A resolution change is one undoable operation.\n\nPS-DES-015  Runtime physical mapping is pixel-based and top-left anchored; no automatic centering or OS display rotation is required.\n\n### 5. Screens, Pages and navigation\n\n### 5.1 Page Flow\n\nPS-FLOW-001  A Screen supports Navigation Flow or Scroll Flow.\n\nPS-FLOW-002  Navigation Flow uses explicit visual Page connections and supports cyclic navigation.\n\nPS-FLOW-003  One Page is designated Start Page.\n\nPS-FLOW-004  Page re-entry can Reset or Restore configured state.\n\nPS-FLOW-005  Back uses runtime navigation history rather than a hard-coded previous Page.\n\nPS-FLOW-006  Scroll Flow composes Pages according to flow order, not their spatial Designer Canvas positions.\n\nPS-FLOW-007  Scroll direction supports Vertical, Horizontal and Horizontal Reverse.\n\nPS-FLOW-008  Scroll Flow may be Free or Snap; snap targets may be Page, Section or Anchor with configurable animation.\n\nPS-FLOW-009  Cyclic/seamless scroll is supported where the content topology permits it.\n\nPS-FLOW-010  Long content within a Page is handled through Scrollable Containers independently of Page Flow.\n\n### 5.2 Page transitions and swipe\n\nPS-TRANS-001  Each Screen has a default Page transition and each navigation connection may override it.\n\nPS-TRANS-002  Transitions support duration, direction, easing and a standard library including instant, fade, slide/move, scale and composited effects.\n\nPS-TRANS-003  Overlay/mask transitions may use a transition asset and configurable swap point.\n\nPS-TRANS-004  Transition architecture must be internally extensible.\n\nPS-TRANS-005  Swipe may act as a trigger and may drive interactive transition progress with cancellation threshold.\n\nPS-TRANS-006  Page transition covers the complete Screen viewport, including persistent Screen-level UI.\n\n### 6. Elements, styling and reusable UI\n\nNative elements include at minimum Button, Text, Image, interactive zone and decorative/visual elements. Functional patterns such as Menu, Gallery, Pagination, Audio, Quiz and other specialized behavior are Widgets.\n\nPS-ELEM-001  Every applicable element supports X/Y/W/H, visibility, layer order, state and event/action binding.\n\nPS-ELEM-002  Buttons support text, background color, background image/fit, border radius, icon/icon size, typography and alignment.\n\nPS-ELEM-003  Text supports project/system font selection, size, color and horizontal/vertical alignment.\n\nPS-ELEM-004  Image supports fit/alignment, crop, image position/scale inside frame, border radius and SVG mask assets.\n\nPS-ELEM-005  Background/fill alpha is independent from element opacity and may be fully transparent.\n\nPS-ELEM-006  Assigned image/SVG content is independent from background fill.\n\nPS-ELEM-007  Screen-level elements may persist across Pages and have per-Page visibility.\n\nPS-ELEM-008  Fixed-to-viewport versus scroll-with-content behavior is configurable where applicable.\n\nPS-ELEM-009  V1 element-editing behavior is the minimum compatibility baseline unless superseded by a stronger V2 behavior.\n\n### 6.1 Components\n\nPS-COMP-001  Components use Master → Instances → local Overrides → Detach.\n\nPS-COMP-002  Master changes propagate to non-overridden instance properties.\n\nPS-COMP-003  Component Library supports All, This Project, Global and Favorites filters.\n\nPS-COMP-004  Global Components are stored locally outside individual projects and are self-contained with required dependencies.\n\nPS-COMP-005  Inserting a Global Component creates an independent project-local Master; no live dependency on the Global source remains.\n\nPS-COMP-006  Deleting or changing a Global Component must not mutate previously created projects.\n\n### 7. Virtual Asset Library and Build\n\n### 7.1 Working Asset Library\n\nPS-ASSET-001  Asset Library is a virtual tree independent from physical source filesystem hierarchy.\n\nPS-ASSET-002  Assets have stable IDs; project references use asset identity rather than raw source path wherever applicable.\n\nPS-ASSET-003  Source files may reside anywhere accessible on the development computer.\n\nPS-ASSET-004  Users can import files through OS picker and drag external files into the Library.\n\nPS-ASSET-005  Drag targets visibly identify the destination virtual folder.\n\nPS-ASSET-006  Users can create, rename and reorganize virtual folders and move registered assets between them without moving original source files.\n\nPS-ASSET-007  Duplicate filename conflicts offer Replace Existing or Add New with deterministic suffixing; batch import may apply a choice to all conflicts.\n\nPS-ASSET-008  Asset deletion is reference-aware and warns when an asset is in use, showing usage locations where practical.\n\nPS-ASSET-009  Missing source files retain their asset record, stable ID and project references until explicitly removed.\n\nPS-ASSET-010  Missing assets can be relinked to a different physical path while preserving identity and references.\n\nPS-ASSET-011  Replace Asset preserves asset ID and propagates the new source to all references.\n\nPS-ASSET-012  Unsupported files may remain visible in the library but cannot be assigned to incompatible properties.\n\n### 7.2 Folder-backed sequences\n\nPS-ASSET-013  A virtual folder may be used as a media sequence source using direct child supported files only; nested folders are independent.\n\nPS-ASSET-014  Sequence ordering supports deterministic default order plus manual drag-and-drop ordering without modifying physical source files.\n\nPS-ASSET-015  The same asset folder may participate in different sequences with different saved ordering.\n\n### 7.3 Build\n\nPS-BUILD-001  Build destination and build/project name are selected by the user.\n\nPS-BUILD-002  Build validates source asset availability before or during materialization and reports missing sources.\n\nPS-BUILD-003  Build recreates the virtual asset structure physically in the destination.\n\nPS-BUILD-004  Build copies all referenced source assets and project fonts required by the Player project.\n\nPS-BUILD-005  Build generates Player-facing project JSON/data using packaged relative paths.\n\nPS-BUILD-006  Player Build has no dependency on original source paths.\n\nPS-BUILD-007  Build is self-contained and suitable for copying, backup and installation.\n\n### 8. Media systems\n\n### 8.1 Media Player\n\nPS-MEDIA-001  Media Player supports per-instance mixed Image + Video Content Sequence.\n\nPS-MEDIA-002  Content items have stable IDs/names and configurable order.\n\nPS-MEDIA-003  Per-item settings include image duration, video range, loop/range loop, volume/mute, playback speed, fit/alignment and transition.\n\nPS-MEDIA-004  Player actions include Play, Pause, Stop, Next, Previous, Go To Item, Restart Current, Seek, Set Volume/Mute, Reset and Close/Exit Overlay.\n\nPS-MEDIA-005  Media events are exposed through the common Action System, including sequence completion.\n\nPS-MEDIA-006  Per-content-item timeline events can execute actions at configured times.\n\nPS-MEDIA-007  Media item transitions include Cut, Fade Out/In, Crossfade, standard transition library, custom transition asset and configurable swap point.\n\nPS-MEDIA-008  Next media item can be preloaded before transition.\n\nPS-MEDIA-009  Media Player can be embedded, full-page, or an Overlay frame spatially edited on the Screen Designer.\n\nPS-MEDIA-010  Multiple Media Players may be designed, but only one system Media Player is active/playing per Screen at a time.\n\nPS-MEDIA-011  Starting another Media Player on the same Screen pauses/displaces the current Player while preserving position; no automatic resume is required unless explicitly configured.\n\nPS-MEDIA-012  Media Players on different Screens remain independent.\n\nPS-MEDIA-013  External/input controls remain available during playback subject to explicit interaction-blocking rules.\n\nPS-MEDIA-014  Configurable exit user action, including keyboard binding, can leave playback.\n\nPS-MEDIA-015  Playback controls are configurable in layout and appearance and preserve V1 Home/Previous/Backward/Play-Pause/Forward/Next/Progress capabilities.\n\nPS-MEDIA-016  Playback controls support custom graphics, separate pause graphic, progress styling, auto-hide and global show/hide.\n\nPS-MEDIA-017  Network commands may directly control playback functions.\n\n### 8.2 Background media and audio\n\nPS-AUDIO-001  Page may use image/video/media playlist background with autonomous looping and configurable audio.\n\nPS-AUDIO-002  Background playback can continue independently from foreground/Overlay Media Player or be explicitly paused/resumed around it.\n\nPS-AUDIO-003  Screen-level and Page-level background audio support autoplay, loop, volume/mute and fade.\n\nPS-AUDIO-004  Media Player may have audio priority using ducking or pause-background-audio behavior.\n\nPS-AUDIO-005  Standard Audio Player Widget supports play/pause, seek/progress, volume/mute, optional waveform/visualizer, appearance customization and events/actions.\n\n### 9. Events, conditions, actions and state\n\nThe common interaction grammar is: Trigger/Event → optional Conditions → one or more Actions.\n\nPS-ACT-001  Native elements and Widgets expose events through a common event contract.\n\nPS-ACT-002  An event can execute multiple actions immediately or as an ordered sequence.\n\nPS-ACT-003  Sequences support Wait and Wait Until.\n\nPS-ACT-004  Conditions support IF/ELSE behavior and project variables.\n\nPS-ACT-005  Trigger re-entry policy supports Ignore, Restart, Queue and Allow Parallel where safe.\n\nPS-ACT-006  Actions include navigation, popup/media control, state changes, variable operations, animation, network send, interaction blocking and other registered product actions.\n\nPS-ACT-007  Delayed commands and V1 command-queue behavior remain representable.\n\nPS-ACT-008  Repeated identical external start commands may advance through a configured content queue and can reset that queue to its initial state.\n\nPS-ACT-009  External command handling may be filtered by source and Screen/runtime context.\n\nPS-ACT-010  Global return-to-previous, return-to-initial and animation-command behaviors remain available through the generalized action system.\n\n### 9.1 Variables\n\nPS-VAR-001  Project has a central Variables Manager with explicit declarations and stable IDs.\n\nPS-VAR-002  Initial scalar types include Text, Number and Boolean.\n\nPS-VAR-003  Variables have human-readable labels, safe rename and default values.\n\nPS-VAR-004  Variables are project-wide within one Player runtime and are accessible across Screens/Pages, Actions, Conditions, Timelines and Widgets.\n\nPS-VAR-005  Widget internal state is separate from project Variables, but Widgets may expose values to project logic.\n\nPS-VAR-006  Actions can Set, Increase, Decrease and Reset variables, selected variables or variable groups.\n\nPS-VAR-007  Separate Player installations do not share implicit global variable memory; cross-computer state coordination must be explicit.\n\n### 10. Animation and timeline\n\nPS-ANIM-001  Object animations support appear, disappear, opacity, scale, move, state change, press/touch/hover reactions, loop and idle animation.\n\nPS-ANIM-002  Animation behavior is applicable to native elements and compatible Widget/Container content.\n\nPS-TIME-001  Each Page may have a finite automation Timeline that starts when the Page is ready.\n\nPS-TIME-002  Timeline events execute standard Actions at configured times.\n\nPS-TIME-003  Timeline event repeat policy supports Every Entry, Once per Visitor Session and Once per Runtime Session where applicable.\n\nPS-TIME-004  Page Timeline restarts from zero on Page entry unless completed-state behavior is configured.\n\nPS-TIME-005  Re-entry can Replay or restore Completed Visual State without replaying side effects.\n\nPS-TIME-006  Visual state restoration is distinct from side-effect execution.\n\nPS-TIME-007  Timeline can block and later re-enable user interaction.\n\nPS-TIME-008  Page remains active after finite Timeline completion unless an explicit action navigates elsewhere.\n\n### 11. Popups, Widgets, Forms and reference-case capabilities\n\nPS-POP-001  Popup is a reusable Screen-level modal entity with arbitrary content, separate Designer frame, open/close actions, backdrop and transition.\n\nPS-POP-002  Popup may enforce modal input blocking; nested Popups are outside initial V2 scope.\n\nPS-WID-001  Internal Widget Framework provides a common contract for properties, events, actions, state, rendering and serialization.\n\nPS-WID-002  Initial product must be capable of Gallery/Slider, Pagination, Menu, Image Viewer/Zoom, Audio Player and generic Form patterns.\n\nPS-WID-003  Image Viewer supports zoom and pan with reset behavior.\n\nPS-WID-004  Quiz and mini-game behavior may be built through Widgets + Variables + Conditions + Actions + States rather than hard-coded project applications.\n\nPS-FORM-001  Form supports designer-defined fields and variable names/schema.\n\nPS-FORM-002  Form submit is an event that may invoke standard Actions.\n\nPS-FORM-003  Form data storage is an implementation strategy/extension point; no visitor-account system is implied.\n\n### 12. Idle / Screensaver\n\nPS-IDLE-001  Idle configuration is per Screen with independent activity tracking and timeout.\n\nPS-IDLE-002  User interaction resets that Screen's idle timer; automated runtime events do not.\n\nPS-IDLE-003  Widgets may emit explicit user-activity events.\n\nPS-IDLE-004  Screensaver is a Screen-level entity/frame reusing the media playback engine.\n\nPS-IDLE-005  Screensaver supports image, video or media sequence plus overlay text/graphics and configurable enter/exit transitions.\n\nPS-IDLE-006  On Idle Start and On Idle End are standard events.\n\nPS-IDLE-007  Screensaver may exit on touch/input or external command.\n\nPS-IDLE-008  Exit scope may affect only the current Screen or all connected synchronized Screens when explicitly configured.\n\nPS-IDLE-009  Idle warning/Continue Interaction flow may be configured before reset.\n\nPS-IDLE-010  Idle reset may execute a configurable reset scenario including variable resets/navigation/media cleanup.\n\n### 13. External control\n\n### 13.1 TCP and UDP\n\nPS-NET-001  Incoming TCP command is a Trigger; outgoing TCP command is an Action.\n\nPS-NET-002  Incoming UDP command is a Trigger; outgoing UDP command is an Action.\n\nPS-NET-003  Commands may use arbitrary raw payload strings; JSON is not mandatory.\n\nPS-NET-004  TCP supports configurable listening ports, destination IP/host and port, and default endpoint.\n\nPS-NET-005  UDP supports configurable listening port, destination IP/host and port.\n\nPS-NET-006  Optional source IP/port filtering is supported.\n\nPS-NET-007  Network commands can navigate, control media, animations, states, idle, scenarios, interaction lock and other Action System capabilities.\n\nPS-NET-008  A dedicated iRidi subsystem is not required initially; iRidi is supported through compatible TCP/UDP control. A dedicated adapter may be added if a real integration requires it.\n\n### 13.2 Keyboard and mouse input\n\nPS-INPUT-001  V1 keyboard playback bindings for Previous/Back/Pause/Forward/Next remain supported and configurable.\n\nPS-INPUT-002  V1 mouse playback bindings remain supported and configurable.\n\nPS-INPUT-003  Keyboard navigation can move UI-button selection and activate the selected button.\n\nPS-INPUT-004  External commands can control UI-button selection.\n\nPS-INPUT-005  Button activation semantics are Touch/Pointer Down → Pressed; release inside executes action; release outside cancels.\n\n### 14. Displays and synchronized installations\n\n### 14.1 Single-PC multi-display\n\nPS-DISP-001  Player detects physical displays and exposes resolution, position, scale/primary metadata and a stable physical identity where the OS permits.\n\nPS-DISP-002  Player local configuration maps logical Screens to physical Displays.\n\nPS-DISP-003  One Screen cannot be assigned to multiple Displays and one Display cannot host multiple Screens simultaneously in the standard mapping model.\n\nPS-DISP-004  Mapping is deployment-local and is not portable project data.\n\nPS-DISP-005  Player creates separate runtime windows for assigned Displays while sharing one local Runtime session.\n\nPS-DISP-006  A missing previously mapped monitor is shown as missing and must not crash other Screens.\n\nPS-DISP-007  No automatic reassignment or hot-plug recovery is required in initial V2.\n\nPS-DISP-008  Identify Displays assists technicians in mapping physical outputs.\n\n### 14.2 Multi-computer synchronized Player\n\nPS-SYNC-001  Multi-computer synchronization is an explicit optional mode, separate from ordinary single-PC multi-display.\n\nPS-SYNC-002  Each computer runs its own Player and its own independently built project/content.\n\nPS-SYNC-003  One Player acts as Master/Server and also participates as a normal playback runtime; others act as Clients.\n\nPS-SYNC-004  Master tracks configured expected/allowed Clients and does not start a synchronized cycle until all required nodes are connected and ready.\n\nPS-SYNC-005  Synchronization protocol includes clock-offset measurement, PREPARE, READY barrier and future absolute START time adjusted by measured offsets.\n\nPS-SYNC-006  Synchronization covers media start, sequence advancement and screensaver where configured.\n\nPS-SYNC-007  External controller may trigger the Master, which coordinates Clients transparently.\n\nPS-SYNC-008  Continuous drift correction is not required in initial V2.\n\nPS-SYNC-009  Player synchronization and external-control configuration are conceptually separate.\n\n### 15. Runtime loading, preloading and performance\n\nPS-PRE-001  Runtime has a Preload Manager and an explicit Ready state.\n\nPS-PRE-002  Initial startup preloads assets needed for the start/current Page and required system UI.\n\nPS-PRE-003  Runtime prepares destination Page assets before display and preloads the next media item where applicable.\n\nPS-PRE-004  Assets may be marked Always Preload.\n\nPS-PRE-005  Preload exposes progress and timeout/error handling.\n\nPS-PRE-006  Missing or invalid media must not terminate the entire Player; sequence playback skips failed items where possible and continues.\n\nPS-PRE-007  Large images/video and repeated user actions must be handled without avoidable freezes.\n\nPS-PRE-008  Player is designed for long-running local/offline museum operation.\n\n### 16. Player, kiosk and lifecycle\n\nPS-PLAY-001  Player is a standalone universal application; it is not rebuilt as a different executable for every project.\n\nPS-PLAY-002  On first run, Player can select/open a Build and remember the selected project in Player-local configuration.\n\nPS-PLAY-003  Player loads a Build once per runtime session; no live filesystem watcher or Constructor→Player synchronization is required.\n\nPS-PLAY-004  Explicit reload/reopen performs full runtime reinitialization and rereads build data.\n\nPS-PLAY-005  Player supports Windows autostart and configurable startup delay including zero.\n\nPS-PLAY-006  Production mode is fullscreen, borderless, cursor-hidden and suppresses visitor-accessible technical UI, context menus and development shortcuts.\n\nPS-PLAY-007  A controlled maintenance exit exists for technicians.\n\nPS-PLAY-008  Player distinguishes expected exit from crash for watchdog behavior.\n\nPS-PLAY-009  Watchdog can restart Player after unexpected termination and includes crash-loop protection.\n\nPS-PLAY-010  After restart, runtime initializes to a known project state.\n\nPS-PLAY-011  Player does not require permanent Internet connectivity.\n\n### 17. Preview, validation and diagnostics\n\n### 17.1 Preview\n\nPS-PREV-001  Constructor provides one Full Runtime Preview; no separate simplified Quick Preview is required.\n\nPS-PREV-002  Preview uses the same Runtime Engine and behavior as Player.\n\nPS-PREV-003  Preview runs as a separate runtime session and supports temporary Screen→Display assignment independent of Player deployment mapping.\n\nPS-PREV-004  Unassigned Screens are permitted in Preview.\n\nPS-PREV-005  Preview uses real TCP/UDP/network behavior rather than simulated commands.\n\n### 17.2 Validation\n\nPS-VAL-001  Constructor provides manual project validation/preflight and automatically runs validation before Build.\n\nPS-VAL-002  Validation reports Errors and Warnings but supports Build Anyway where policy permits.\n\nPS-VAL-003  Problems reference affected Screen/Page/object/property and provide Go to Problem navigation.\n\nPS-VAL-004  Validation includes missing assets/fonts, invalid references and other conditions that can prevent correct runtime behavior.\n\n### 17.3 Developer Overlay and logs\n\nPS-DIAG-001  Player/Preview Developer Overlay is available through a configurable technician hotkey.\n\nPS-DIAG-002  Overlay exposes system/runtime status, current Screen, loaded project data, TCP/UDP command log, variables, events/actions, media/preload and synchronization diagnostics as applicable.\n\nPS-DIAG-003  Developer tools may manually send network commands for diagnostics.\n\nPS-DIAG-004  Logging supports levels, a unified runtime API, persistent rotating logs and live Overlay display.\n\nPS-DIAG-005  Technical failures are logged in detail but are not shown to visitors as raw technical UI.\n\n### 18. Content Admin Mode\n\nPS-ADMIN-001  Content Admin is a restricted mode of the same Constructor application, not a separate required product.\n\nPS-ADMIN-002  Developer explicitly exposes editable properties/operations to Content Admin.\n\nPS-ADMIN-003  Typical exposed content includes text, labels, images, video, backgrounds, media sequences and selected asset operations.\n\nPS-ADMIN-004  Content Admin does not expose Screen/Page structure, geometry, Canvas authoring, Actions, Variables, Timelines or other functional logic unless a future explicit capability adds it.\n\nPS-ADMIN-005  Admin edits modify the Working Project/source model; deployed Player behavior changes only after a new Build is created and deployed.\n\nPS-ADMIN-006  Original brief capability to add arbitrary cards/blocks is revised: structural creation is not part of initial restricted Admin Mode.\n\n### 19. Visual system, fonts and SVG import\n\n### 19.1 Project visual system\n\nPS-STYLE-001  Project Settings provide default typography and default appearance for newly created native elements.\n\nPS-STYLE-002  Project Color Palette contains built-in semantic color variables and arbitrary user-defined color variables.\n\nPS-STYLE-003  Color-capable properties can use a literal color or reference a palette variable.\n\nPS-STYLE-004  Changing a referenced color variable propagates to all properties using that variable.\n\nPS-STYLE-005  Color variables have stable IDs and safe rename.\n\nPS-STYLE-006  Default styles may reference color variables; literal values do not retroactively follow later default changes.\n\nPS-STYLE-007  Full multiple-theme/skin switching is deferred from initial V2.\n\n### 19.2 Project fonts\n\nPS-FONT-001  TTF and OTF files can be registered as Project Font assets with family/weight/style metadata.\n\nPS-FONT-002  Project Settings define default font family for newly created text.\n\nPS-FONT-003  Elements may override project default font.\n\nPS-FONT-004  Player loads packaged Project Fonts from the Build; Windows installation is not required.\n\nPS-FONT-005  System-installed fonts remain available for V1 compatibility, but Project Fonts are preferred for portable builds.\n\nPS-FONT-006  Missing required fonts are reported by validation.\n\n### 19.3 Structured SVG import\n\nPS-SVG-001  Constructor imports ordinary SVG, including Figma-exported SVG, into an editable structured object tree.\n\nPS-SVG-002  Import preserves groups, primitives, text, images, geometry/transforms, fill/stroke/opacity and clip/mask information where supported.\n\nPS-SVG-003  SVG groups map to Containers where appropriate.\n\nPS-SVG-004  External SVG assets are registered/materialized through the project asset system.\n\nPS-SVG-005  Unsupported constructs should preserve visual fidelity as far as practical rather than silently disappearing.\n\nPS-SVG-006  No special Figma naming convention or semantic IDs are required; interaction semantics are assigned after import.\n\nPS-SVG-007  Native Figma API/plugin integration is a future extension, not initial V2 requirement.\n\n### 20. Templates and local reusable libraries\n\nPS-TPL-001  Save as Template stores a self-contained snapshot of a complete Working Project and required dependencies in a local Constructor template library.\n\nPS-TPL-002  New Project can be created Blank or From Template.\n\nPS-TPL-003  A project created from a Template is independent; later Template changes do not propagate.\n\nPS-TPL-004  Constructor application updates must preserve user Projects, Templates and Global Components where format compatibility permits.\n\n### 21. Trial-build protection and application updates\n\nPS-TRIAL-001  A temporary test Constructor build may embed an expiration date and block editor use after expiration without deleting user projects.\n\nPS-TRIAL-002  Player projects do not expire by default.\n\nPS-TRIAL-003  This mechanism is not a commercial licensing platform.\n\nPS-UPD-001  Application updates are manual; no automatic online update service/check is required.\n\nPS-UPD-002  New Constructor/Player binaries are distributed by the developer and should preserve compatible local user data/configuration.\n\n### 22. Initial V2 non-goals / deferred capabilities\n\n- Full multi-theme / runtime skin switching engine.\n\n- Native Figma API/plugin import.\n\n- Public third-party Widget SDK, marketplace or plugin ecosystem.\n\n- Automatic online application update service.\n\n- Commercial licensing/subscription infrastructure.\n\n- Persistent project checkpoints/version history.\n\n- Responsive web-style breakpoint system.\n\n- Automatic display hot-plug recovery/reassignment.\n\n- Continuous cross-computer playback drift correction.\n\n- Implicit shared Variables across separate Player installations.\n\n- Nested Popups.\n\n- Full vector-mask authoring editor.\n\n- DAW-class audio editing/mixing subsystem.\n\n### 23. Traceability and compatibility baseline\n\nThe implementation backlog must retain source provenance for requirements from four registries: V1-F001…V1-F178, TZ-F001…TZ-F128, CASE-F001…CASE-F048, and NEW-F001…NEW-F895. Historical NEW requirements that were superseded remain in the decision registry and must not be reactivated merely because their wording resembles the final architecture.\n\n### 23.1 Explicit reconciliations\n\n- Build is ACTIVE. Earlier 'no build / Player reads Working Project directly' decisions are superseded by the final Working Project → Build → Player architecture.\n\n- Asset Library is virtual. Earlier mandatory physical Project Folder / mirrored filesystem requirements are superseded where they conflict.\n\n- External drag-and-drop asset import is ACTIVE; the earlier prohibition is superseded.\n\n- Project orientation is represented by Screen width × height; no separate OS-rotation/orientation parameter is required.\n\n- Original multi-theme requirement is partially deferred; live project color variables/defaults/components/fonts provide initial reskin infrastructure.\n\n- Dedicated iRidi integration is revised to generic TCP/UDP control unless a real deployment requires a special adapter.\n\n- Content Admin does not structurally add arbitrary Screens/Pages/cards in initial V2; this narrows the original brief intentionally.\n\n- Content Admin changes require a new Build/deployment to affect Player.\n\n- Cross-computer Variables are not transparently shared; synchronized behavior is explicit.\n\n- Project Fonts are packaged into Build, not required to be installed in Windows.\n\n- Global Component dependencies must remain self-contained but must conform to the final virtual-asset/build model.\n\n### 24. Product-level acceptance criteria\n\nAC-01  An author can build both page-navigation and scroll-based museum applications in one product.\n\nAC-02  A project can reproduce the documented reference patterns: menus, cards, popups, galleries, zoomable images, long scrolling content, animated transitions and stateful interactive/game-like flows.\n\nAC-03  A V1 project capability has an equivalent or stronger V2 mechanism; no confirmed V1 feature is silently absent.\n\nAC-04  An author can create a project using source assets scattered across the development machine, save instantly without copying all media, and later produce a self-contained Build.\n\nAC-05  A Player machine can run the Build with no access to the original development-machine paths and no mandatory Internet connection.\n\nAC-06  Preview behavior matches Player behavior because both use the same Runtime Engine.\n\nAC-07  Single-PC multi-display and multi-PC synchronized installations operate as separate, explicit topologies.\n\nAC-08  External TCP/UDP control can trigger the same product logic available to on-screen interaction.\n\nAC-09  Runtime failures in individual assets/elements degrade gracefully and remain diagnosable without exposing technical errors to visitors.\n\nAC-10  A technician can validate, map displays, inspect diagnostics, and recover/restart an installation without modifying project design.\n\n### 25.
